#001 2026-08-03

「作る」より先に「決める」を置く運用に切り替えた

これまでは、まとまった時間ができたときに何を作るか考え始めていた。それだと、考えているうちに時間が終わる。順番が逆だった。

時間を2種類に分けることにした。細切れの時間は考えて言語化するために使い、まとまった時間は実装させて確認するために使う。 考える作業に PC は要らない。移動中でも待ち時間でも、スマホから GitHub の Web エディタで仕様書は書ける。

やったこと

  • CLAUDE.md — この PJ の前提・デザイン規約・やらないこと・確認工程を明文化。AI に毎回説明し直す手間をなくす
  • docs/specs/ — 仕様書置き場。テンプレートと運用ルール
  • docs/specs/001-hub-site.md — 既に動いているトップページを、後から仕様書に起こした
  • log/ — このページ

決めたこと

  • AI への指示は「◯◯を作って」ではなく「docs/specs/00X-*.md を読んで、この通りに実装して」から始める
  • 仕様に書いていない判断が必要になったら、AI に埋めさせず質問させる。空白を勝手に埋められると、後で「なぜこうなっているか」を自分で説明できなくなる
  • 実装が仕様とずれたら、コードではなく仕様書を先に直す
  • 完成後に必ずセキュリティレビューをかける。さらに同じ成果物を別の AI にもレビューさせる — 指摘がずれた箇所こそ読む価値がある

気づき

既存のトップページを仕様書に起こす作業（001）が、思っていたより効いた。動いているものを言葉にしようとすると、自分でも決めていなかった箇所が出てくる。「TH のアプリが0件のとき何を出すのが正しいのか」「PWA でリンクを乗っ取ると target="_blank" はどうなるのか」——コードには答えが書いてあったが、意図は書いていなかった。

作れるかどうかより、何を作りたいか・どう動いてほしいかを具体的に言葉にできるかどうか。

次にやること

  • 次の成果物は「人からデータを受け取って、保存して、集計する」もの。今のアプリは全部その手前で止まっている
  • 手を動かして詰まった箇所を特定してから、その領域だけ学び直す。順番を逆にしない
